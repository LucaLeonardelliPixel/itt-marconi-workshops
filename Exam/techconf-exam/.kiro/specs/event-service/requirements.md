# event-service — Requirements

**Service:** event-service  
**Base path:** `/api/v1/events`  
**Development port:** `5002`  
**Contract:** `contracts/openapi/event-service.yaml`  
**Source:** `Exam.MD` §5.2 and §4  
**Status:** Mandatory

---

## 1. Purpose and Scope

The event-service manages TechConf conference events, including their location, schedule, capacity, price, organizer, and lifecycle. It owns event data and calls user-service to verify that each referenced organizer exists and has role `organizer`.

### Primary actor stories

- As an organizer, I want to create and maintain conference events so that attendees can discover accurate event information.
- As a platform client, I want to browse and filter events with pagination so that event catalogues remain manageable.
- As the registration-service, I want to retrieve event status, capacity, and price so that registrations can enforce availability and pricing rules.
- As a platform operator, I want dependency failures reported consistently so that callers can distinguish invalid references from temporary outages.

## 2. Event Resource

### 2.1 Writable fields

| Field | Type | Required on POST/PUT | Constraints and default |
|---|---|---:|---|
| `title` | string | Yes | 3–120 characters |
| `description` | string or null | No | Maximum 2000 characters; default `null` |
| `organizer_id` | UUID string | Yes | Must identify an existing user whose role is `organizer` |
| `venue` | string | Yes | Maximum 100 characters |
| `city` | string | Yes | Maximum 60 characters |
| `start_date` | date string | Yes | ISO date `YYYY-MM-DD` |
| `end_date` | date string | Yes | ISO date `YYYY-MM-DD`; must be on or after `start_date` |
| `capacity` | integer | Yes | 1–10000 inclusive; booleans are not integers |
| `price` | number | Yes | At least `0.00`; EUR is implicit |
| `status` | enum | No | `draft`, `published`, or `cancelled`; default `draft` |

PATCH accepts any non-empty subset of these writable fields. Request bodies do not accept additional properties.

### 2.2 Read-only fields

| Field | Type | Requirement |
|---|---|---|
| `id` | UUID v4 string | Generated by the event-service and never accepted from clients |
| `created_at` | ISO 8601 UTC datetime | Set once at creation |
| `updated_at` | ISO 8601 UTC datetime | Set at creation and refreshed after every successful modification |

### 2.3 Response shape

Every successful event representation SHALL contain only the fields declared by the OpenAPI `Event` schema. Optional nullable fields MAY be omitted or returned as `null`; all contract-required fields SHALL be present.

## 3. Business Rules

### REQ-EVT-B01 — Organizer reference must exist

**User story:** As the platform owner, I want every event linked to an existing user so that events never reference unknown organizers.

**Acceptance criteria:**

1. WHEN a request creates an event with `organizer_id` THEN the event-service SHALL call `GET {USER_SERVICE_URL}/api/v1/users/{organizer_id}` with a two-second timeout before persisting the event.
2. WHEN a PUT request supplies `organizer_id` THEN the event-service SHALL validate the organizer reference before replacing the event.
3. WHEN a PATCH request changes `organizer_id` THEN the event-service SHALL validate the new organizer reference before updating the event.
4. IF user-service responds `404` for the supplied organizer THEN the event-service SHALL respond `422 Unprocessable Entity` with error code `REFERENCE_NOT_FOUND` and SHALL NOT persist the requested change.

### REQ-EVT-B02 — Organizer must have organizer role

**User story:** As the platform owner, I want only organizer users to own events so that attendee and speaker accounts cannot administer conferences.

**Acceptance criteria:**

1. WHEN user-service returns a user for `organizer_id` AND the user's `role` is `organizer` THEN the event-service SHALL accept the organizer reference.
2. IF user-service returns a user whose `role` is not `organizer` THEN the event-service SHALL respond `422 Unprocessable Entity` with error code `INVALID_ORGANIZER` and SHALL NOT persist the requested change.

### REQ-EVT-B03 — Valid event date range

**User story:** As an attendee, I want event dates to be chronologically valid so that event schedules are understandable.

**Acceptance criteria:**

1. WHEN `start_date` and `end_date` are valid ISO dates AND `end_date` is on or after `start_date` THEN the event-service SHALL accept the date range.
2. IF `end_date` precedes `start_date` THEN the event-service SHALL respond `422 Unprocessable Entity` with error code `VALIDATION_ERROR`.
3. IF either date is not a real date in `YYYY-MM-DD` format THEN the event-service SHALL respond `422 Unprocessable Entity` with error code `VALIDATION_ERROR`.
4. WHEN PUT or PATCH changes either boundary THEN the event-service SHALL validate the resulting complete date range before persisting it.

### REQ-EVT-B04 — Event status lifecycle

**User story:** As an organizer, I want controlled event lifecycle transitions so that published or cancelled events cannot return to invalid states.

**Acceptance criteria:**

1. WHEN an existing event transitions from `draft` to `published` THEN the event-service SHALL accept the transition.
2. WHEN an existing event transitions from `draft` to `cancelled` THEN the event-service SHALL accept the transition.
3. WHEN an existing event transitions from `published` to `cancelled` THEN the event-service SHALL accept the transition.
4. WHEN an update supplies the event's current status THEN the event-service SHALL treat it as an idempotent no-op status assignment and SHALL validate and apply any other supplied fields.
5. IF an existing event attempts any other status transition, including `published` to `draft`, `cancelled` to `draft`, or `cancelled` to `published`, THEN the event-service SHALL respond `422 Unprocessable Entity` with error code `INVALID_STATUS_TRANSITION`.
6. WHEN `status` is omitted during creation THEN the event-service SHALL assign `draft`.

### REQ-EVT-B05 — user-service dependency availability

**User story:** As an API consumer, I want upstream failures distinguished from invalid organizers so that temporary outages can be retried safely.

**Acceptance criteria:**

1. IF a required user-service call times out, is refused, cannot connect, or returns any `5xx` response THEN the event-service SHALL respond `503 Service Unavailable` with error code `DEPENDENCY_UNAVAILABLE`.
2. WHEN the event-service returns `DEPENDENCY_UNAVAILABLE` THEN the error details SHALL identify `user-service` as the unavailable dependency without exposing stack traces or internal exceptions.
3. IF organizer validation cannot complete because user-service is unavailable THEN the event-service SHALL NOT persist the requested event creation or modification.
4. WHEN an endpoint does not require organizer validation, such as list, get, or delete, THEN the event-service SHALL NOT call user-service.

### REQ-EVT-B06 — Event list filtering

**User story:** As a platform client, I want to filter events by status and city so that I can find relevant conferences.

**Acceptance criteria:**

1. WHEN `GET /api/v1/events` includes a valid `status` parameter THEN the event-service SHALL return only events whose status equals that value.
2. WHEN `GET /api/v1/events` includes a `city` parameter THEN the event-service SHALL return only events matching that city.
3. WHEN both `status` and `city` are supplied THEN the event-service SHALL combine the filters with logical AND.
4. IF `status` is not one of `draft`, `published`, or `cancelled` THEN the event-service SHALL respond `422 Unprocessable Entity` with error code `VALIDATION_ERROR`.
5. WHEN filters are active THEN the paginated response `total` SHALL equal the number of matching events before page slicing.

## 4. Endpoint Requirements

### REQ-EVT-E01 — Create event

**Endpoint:** `POST /api/v1/events`

**User story:** As an organizer, I want to create a conference event so that it can enter the TechConf lifecycle.

**Acceptance criteria:**

1. WHEN the request body is valid, the organizer exists with role `organizer`, and all business rules pass THEN the event-service SHALL create the event and respond `201 Created` with an OpenAPI-compliant `Event` body.
2. WHEN creation succeeds THEN the event-service SHALL generate a UUID v4 `id`, set UTC `created_at` and `updated_at`, and set omitted `status` to `draft`.
3. WHEN creation succeeds THEN the event-service SHALL include `Location: /api/v1/events/{id}`.
4. IF the request body is malformed JSON THEN the event-service SHALL respond `400 Bad Request` using the standard error envelope.
5. IF a required field is absent, an unknown field is supplied, or a field violates its schema constraint THEN the event-service SHALL respond `422 Unprocessable Entity` with error code `VALIDATION_ERROR`.
6. IF the organizer reference is missing or invalid THEN the event-service SHALL apply REQ-EVT-B01 and REQ-EVT-B02.
7. IF user-service is unavailable THEN the event-service SHALL apply REQ-EVT-B05.

### REQ-EVT-E02 — List events

**Endpoint:** `GET /api/v1/events?page=&page_size=&status=&city=`

**User story:** As a platform client, I want a paginated event catalogue so that large result sets can be consumed predictably.

**Acceptance criteria:**

1. WHEN no pagination parameters are supplied THEN the event-service SHALL use `page=1` and `page_size=20`.
2. WHEN valid pagination and filter parameters are supplied THEN the event-service SHALL respond `200 OK` with `{"items": [...], "page": page, "page_size": page_size, "total": total}`.
3. IF `page` is not an integer of at least 1 THEN the event-service SHALL respond `422 Unprocessable Entity` with error code `VALIDATION_ERROR`.
4. IF `page_size` is not an integer from 1 through 100 THEN the event-service SHALL respond `422 Unprocessable Entity` with error code `VALIDATION_ERROR`.
5. WHEN the requested page has no matching items THEN the event-service SHALL respond `200 OK` with an empty `items` array and the correct `total`.
6. WHEN filters are supplied THEN the event-service SHALL apply REQ-EVT-B06 before pagination.

### REQ-EVT-E03 — Get event by ID

**Endpoint:** `GET /api/v1/events/{id}`

**User story:** As a platform client or registration-service, I want to retrieve one event so that I can use its current status, capacity, and price.

**Acceptance criteria:**

1. WHEN `{id}` identifies an existing event THEN the event-service SHALL respond `200 OK` with the OpenAPI-compliant `Event` body.
2. IF `{id}` does not identify an existing event THEN the event-service SHALL respond `404 Not Found` with error code `NOT_FOUND`.

### REQ-EVT-E04 — Replace event

**Endpoint:** `PUT /api/v1/events/{id}`

**User story:** As an organizer, I want to replace all mutable event data so that the event record reflects a complete submitted state.

**Acceptance criteria:**

1. WHEN `{id}` exists and the complete request body satisfies schema, organizer, date, and lifecycle rules THEN the event-service SHALL replace all mutable fields, preserve `id` and `created_at`, refresh `updated_at`, and respond `200 OK`.
2. IF `{id}` does not identify an existing event THEN the event-service SHALL respond `404 Not Found` with error code `NOT_FOUND` and SHALL NOT call user-service.
3. IF the replacement body omits a required `EventCreate` field, contains an unknown field, or violates a field constraint THEN the event-service SHALL respond `422 Unprocessable Entity` with error code `VALIDATION_ERROR`.
4. IF organizer validation fails THEN the event-service SHALL apply REQ-EVT-B01, REQ-EVT-B02, or REQ-EVT-B05 as applicable.
5. IF the replacement requests an invalid status transition THEN the event-service SHALL apply REQ-EVT-B04.

### REQ-EVT-E05 — Partially update event

**Endpoint:** `PATCH /api/v1/events/{id}`

**User story:** As an organizer, I want to update selected event fields so that unchanged information remains intact.

**Acceptance criteria:**

1. WHEN `{id}` exists and a non-empty partial body satisfies all relevant rules THEN the event-service SHALL update only supplied mutable fields, preserve all other fields, refresh `updated_at`, and respond `200 OK`.
2. IF `{id}` does not identify an existing event THEN the event-service SHALL respond `404 Not Found` with error code `NOT_FOUND` and SHALL NOT call user-service.
3. IF the body is empty, contains an unknown or read-only field, or a supplied field violates its constraint THEN the event-service SHALL respond `422 Unprocessable Entity` with error code `VALIDATION_ERROR`.
4. WHEN `organizer_id` is supplied and differs from the stored value THEN the event-service SHALL validate it under REQ-EVT-B01, REQ-EVT-B02, and REQ-EVT-B05.
5. WHEN either date or `status` is supplied THEN the event-service SHALL validate the resulting record under REQ-EVT-B03 and REQ-EVT-B04 before persisting it.

### REQ-EVT-E06 — Delete event

**Endpoint:** `DELETE /api/v1/events/{id}`

**User story:** As an organizer, I want to remove an event so that obsolete records no longer appear in the catalogue.

**Acceptance criteria:**

1. WHEN `{id}` identifies an existing event THEN the event-service SHALL remove it and respond `204 No Content` with an empty body.
2. IF `{id}` does not identify an existing event THEN the event-service SHALL respond `404 Not Found` with error code `NOT_FOUND`.

### REQ-EVT-E07 — Health check

**Endpoint:** `GET /health`

**Acceptance criteria:**

1. WHEN `/health` is requested THEN the event-service SHALL respond `200 OK` with exactly `{"status": "ok", "service": "event-service"}`.
2. WHEN user-service is unavailable THEN the event-service health endpoint SHALL continue to report the local event-service process as healthy and SHALL NOT call user-service.

## 5. Error Contract

### REQ-EVT-ERR01 — Standard error envelope

**Acceptance criteria:**

1. WHEN the event-service returns any declared `400`, `404`, `422`, or `503` response THEN the response SHALL be JSON and SHALL match:

```json
{
  "error": {
    "code": "UPPER_SNAKE_CASE",
    "message": "Human-readable explanation",
    "details": {}
  }
}
```

2. WHEN no structured details are needed THEN `details` MAY be omitted because it is optional in the OpenAPI contract; if present it SHALL be a JSON object.
3. IF an error response includes properties not declared by the OpenAPI `Error` schema THEN the response SHALL be considered non-compliant.

| Condition | HTTP status | Required code |
|---|---:|---|
| Malformed JSON | 400 | `MALFORMED_JSON` |
| Event not found | 404 | `NOT_FOUND` |
| Invalid schema field, date, pagination, or filter | 422 | `VALIDATION_ERROR` |
| Organizer user not found | 422 | `REFERENCE_NOT_FOUND` |
| User exists but is not an organizer | 422 | `INVALID_ORGANIZER` |
| Forbidden event status transition | 422 | `INVALID_STATUS_TRANSITION` |
| user-service unavailable or returns 5xx | 503 | `DEPENDENCY_UNAVAILABLE` |

## 6. Platform and Persistence Requirements

### REQ-EVT-N01 — Runtime configuration

1. WHEN the event-service starts THEN it SHALL read `PORT` from the environment and SHALL default to `5002` only when the variable is absent.
2. WHEN an organizer must be validated THEN the event-service SHALL build the request URL from `USER_SERVICE_URL`, defaulting dynamically to `http://localhost:5001` only when the variable is absent.
3. IF the acceptance suite supplies alternate ports or service URLs THEN the event-service SHALL use those supplied values without code changes.

### REQ-EVT-N02 — Pluggable standard-library persistence

1. WHEN `STORAGE_BACKEND` is absent or equals `memory` THEN the event-service SHALL use in-process memory persistence.
2. WHEN `STORAGE_BACKEND=json` THEN the event-service SHALL persist event records under `DATA_DIR` using Python's standard `json` and file APIs.
3. WHEN `STORAGE_BACKEND=sqlite` THEN the event-service SHALL persist event records under `DATA_DIR` using Python's standard `sqlite3` module.
4. WHEN `DATA_DIR` is absent THEN file-backed adapters SHALL use `./data` relative to the service working directory.
5. IF the storage backend changes between `memory`, `json`, and `sqlite` THEN no route or business-rule implementation SHALL require modification.
6. The event-service SHALL NOT require or import an external DBMS or ORM.

### REQ-EVT-N03 — Testability and quality

1. WHEN unit tests execute THEN user-service HTTP behavior SHALL be mockable through the user repository/client abstraction.
2. WHEN repository tests execute THEN identical repository behavior SHALL be verified for `memory`, `json`, and `sqlite`, using `tmp_path` for file-backed stores.
3. WHEN endpoint tests execute THEN at least one response for every endpoint SHALL be validated with `contracts/validator.py::assert_matches_contract`.
4. WHEN coverage is measured for the event-service application package THEN line coverage SHALL be at least 80%.
5. WHEN custom cross-service integration tests execute THEN they SHALL cover one valid organizer, one missing organizer producing 422, and one unavailable user-service producing 503 using real service processes on free ports.
