# registration-service — Requirements

**Service:** registration-service  
**Base path:** `/api/v1/registrations`  
**Development port:** `5003`  
**Contract:** `contracts/openapi/registration-service.yaml`  
**Source:** `Exam.MD` §5.3 and §4  
**Status:** Mandatory

---

## 1. Purpose and User Stories

The registration-service manages user registrations for TechConf events. It owns registration records and calls user-service and event-service to validate references, event publication status, capacity, and registration price.

- As an attendee, I want to register for a published event so that my place is confirmed.
- As an attendee, I want to cancel a confirmed registration so that the seat becomes available again.
- As an organizer, I want event registration statistics so that I can monitor confirmed and available seats.
- As a platform operator, I want duplicate registrations, full events, invalid references, and dependency outages reported with distinct errors.

---

## 2. Registration Resource

### 2.1 Client-writable fields

| Field | Type | POST | PATCH | Constraints |
|---|---|---:|---:|---|
| `user_id` | UUID string | Required | Forbidden | Must exist in user-service |
| `event_id` | UUID string | Required | Forbidden | Must exist in event-service and reference a published event |
| `status` | enum | Forbidden/read-only | Required | PATCH accepts only `cancelled`; resource enum is `confirmed` or `cancelled` |

### 2.2 Server-owned fields

| Field | Type | Requirement |
|---|---|---|
| `id` | UUID v4 string | Generated by registration-service; never accepted from a client |
| `amount` | number | Copied from `event.price` when registration is created; never accepted from a client |
| `status` | enum | Always `confirmed` at creation |
| `created_at` | ISO 8601 UTC datetime | Set at creation and never changed |
| `updated_at` | ISO 8601 UTC datetime | Set at creation and refreshed after successful cancellation |

POST bodies accept exactly `user_id` and `event_id`. PATCH bodies accept exactly one required property, `status`. Additional properties are forbidden.

## 3. Business Rules

### REQ-REG-B01 — User reference must exist

**User story:** As the platform owner, I want registrations linked to real users so that orphan registrations cannot be created.

**Acceptance criteria:**

1. WHEN a valid registration request is received THEN the registration-service SHALL call `GET {USER_SERVICE_URL}/api/v1/users/{user_id}` with a two-second timeout.
2. WHEN user-service returns `200` for `user_id` THEN the registration-service SHALL continue registration validation.
3. IF user-service returns `404` for `user_id` THEN the registration-service SHALL respond `422 Unprocessable Entity` with error code `REFERENCE_NOT_FOUND` and SHALL NOT create a registration.

### REQ-REG-B02 — Event reference must exist

**User story:** As the platform owner, I want registrations linked to real events so that invalid event references are rejected.

**Acceptance criteria:**

1. WHEN user validation succeeds THEN the registration-service SHALL call `GET {EVENT_SERVICE_URL}/api/v1/events/{event_id}` with a two-second timeout.
2. WHEN event-service returns `200` for `event_id` THEN the registration-service SHALL continue event business validation.
3. IF event-service returns `404` during registration creation THEN the registration-service SHALL respond `422 Unprocessable Entity` with error code `REFERENCE_NOT_FOUND` and SHALL NOT create a registration.

### REQ-REG-B03 — Event must be open

**User story:** As an organizer, I want registrations accepted only for published events so that draft or cancelled events cannot receive attendees.

**Acceptance criteria:**

1. WHEN event-service returns an event whose `status` is `published` THEN the registration-service SHALL continue registration validation.
2. IF the referenced event has status `draft` or `cancelled` THEN the registration-service SHALL respond `422 Unprocessable Entity` with error code `EVENT_NOT_OPEN` and SHALL NOT create a registration.

### REQ-REG-B04 — Prevent duplicate confirmed registrations

**User story:** As an attendee, I want only one active registration per event so that duplicate seats are not reserved.

**Acceptance criteria:**

1. WHEN no confirmed registration exists for the same `(user_id, event_id)` THEN the registration-service SHALL permit creation to continue.
2. IF a confirmed registration already exists for the same `(user_id, event_id)` THEN the registration-service SHALL respond `409 Conflict` with error code `ALREADY_REGISTERED`.
3. WHEN a prior registration for the pair is `cancelled` and no confirmed registration remains THEN the registration-service SHALL permit a new confirmed registration.

### REQ-REG-B05 — Enforce event capacity

**User story:** As an organizer, I want confirmed registrations capped at event capacity so that venue limits are never exceeded.

**Acceptance criteria:**

1. WHEN the number of confirmed registrations for `event_id` is less than `event.capacity` THEN the registration-service SHALL permit creation.
2. IF confirmed registrations for `event_id` are greater than or equal to `event.capacity` THEN the registration-service SHALL respond `409 Conflict` with error code `EVENT_FULL`.
3. WHEN capacity is evaluated THEN the registration-service SHALL exclude cancelled registrations from the confirmed count.
4. WHEN concurrent registration requests are evaluated THEN persistence SHALL atomically prevent the number of confirmed registrations from exceeding the validated capacity.

### REQ-REG-B06 — Copy event price

**User story:** As an attendee, I want my registration amount fixed from the event price so that clients cannot choose or alter the charge.

**Acceptance criteria:**

1. WHEN a registration is created THEN the registration-service SHALL set `amount` equal to the `price` returned by event-service.
2. IF a POST body contains `amount` THEN the registration-service SHALL respond `422 Unprocessable Entity` with error code `VALIDATION_ERROR`.
3. WHEN the event price changes after registration THEN the registration-service SHALL retain the amount captured at registration creation.

### REQ-REG-B07 — Registration cancellation lifecycle

**User story:** As an attendee, I want to cancel a confirmed registration so that its seat is released.

**Acceptance criteria:**

1. WHEN PATCH requests `status=cancelled` for a confirmed registration THEN the registration-service SHALL update the status, refresh `updated_at`, and respond `200 OK`.
2. WHEN a confirmed registration becomes cancelled THEN the registration-service SHALL exclude it from duplicate and capacity counts immediately.
3. IF PATCH requests `cancelled` to `confirmed`, `confirmed` to `confirmed`, `cancelled` to `cancelled`, or any status other than `cancelled` THEN the registration-service SHALL respond `422 Unprocessable Entity` with error code `INVALID_STATUS_TRANSITION`.
4. IF PATCH contains fields other than the required `status` THEN the registration-service SHALL respond `422 Unprocessable Entity` with error code `VALIDATION_ERROR`.

### REQ-REG-B08 — Event registration statistics

**User story:** As an organizer, I want capacity statistics for an event so that I can see confirmed registrations and available seats.

**Acceptance criteria:**

1. WHEN `GET /api/v1/registrations/stats?event_id={id}` references an existing event THEN the registration-service SHALL respond `200 OK` with exactly `event_id`, `capacity`, `confirmed`, and `available`.
2. WHEN statistics are calculated THEN `confirmed` SHALL equal the number of registrations with status `confirmed` for the event.
3. WHEN statistics are calculated THEN `available` SHALL equal `max(event.capacity - confirmed, 0)`.
4. IF event-service returns `404` for the statistics `event_id` THEN the registration-service SHALL respond `404 Not Found` with error code `NOT_FOUND`.
5. IF `event_id` is absent or is not a valid UUID THEN the registration-service SHALL respond `422 Unprocessable Entity` with error code `VALIDATION_ERROR` without calling event-service.

### REQ-REG-B09 — Dependency unavailable

**User story:** As an API consumer, I want temporary dependency failures identified explicitly so that requests can be retried safely.

**Acceptance criteria:**

1. IF a required user-service or event-service call times out, is refused, cannot connect, returns malformed/unusable data, or returns `5xx` THEN the registration-service SHALL respond `503 Service Unavailable` with error code `DEPENDENCY_UNAVAILABLE`.
2. WHEN `DEPENDENCY_UNAVAILABLE` is returned THEN `details` SHALL identify the unavailable dependency without exposing stack traces or internal exception text.
3. IF dependency validation cannot complete THEN the registration-service SHALL NOT create or mutate a registration.
4. WHEN list, get, patch, or delete operates only on local registration data THEN the registration-service SHALL NOT call user-service or event-service.

## 4. Endpoint Requirements

### REQ-REG-E01 — Create registration

**Endpoint:** `POST /api/v1/registrations`

**Acceptance criteria:**

1. WHEN the JSON body contains valid `user_id` and `event_id`, both references exist, the event is published, no confirmed duplicate exists, and capacity is available THEN the registration-service SHALL create a registration and respond `201 Created`.
2. WHEN creation succeeds THEN the registration-service SHALL generate UUID v4 `id`, copy event `price` to `amount`, set status `confirmed`, and set UTC `created_at` and `updated_at`.
3. WHEN creation succeeds THEN the registration-service SHALL include `Location: /api/v1/registrations/{id}` and return an OpenAPI-compliant `Registration` body.
4. IF the request body is malformed JSON THEN the registration-service SHALL respond `400 Bad Request` with error code `MALFORMED_JSON`.
5. IF the body is not an object, omits `user_id` or `event_id`, contains server-owned/unknown fields, or contains invalid UUIDs THEN the registration-service SHALL respond `422 Unprocessable Entity` with error code `VALIDATION_ERROR`.
6. IF reference, event-state, duplicate, capacity, or dependency validation fails THEN the registration-service SHALL return the status and code defined by REQ-REG-B01 through REQ-REG-B09 and SHALL NOT create a record.

### REQ-REG-E02 — List registrations

**Endpoint:** `GET /api/v1/registrations?page=&page_size=&user_id=&event_id=&status=`

**Acceptance criteria:**

1. WHEN no pagination parameters are supplied THEN the registration-service SHALL use `page=1` and `page_size=20`.
2. WHEN valid parameters are supplied THEN the registration-service SHALL respond `200 OK` with `{"items": [...], "page": page, "page_size": page_size, "total": total}`.
3. WHEN `user_id`, `event_id`, or `status` filters are supplied THEN the registration-service SHALL apply all supplied filters with logical AND before pagination.
4. WHEN filters are active THEN `total` SHALL equal the number of matching registrations before page slicing.
5. IF `page` is not an integer of at least 1, `page_size` is not from 1 through 100, a UUID filter is invalid, or status is not `confirmed` or `cancelled` THEN the registration-service SHALL respond `422 Unprocessable Entity` with error code `VALIDATION_ERROR`.
6. WHEN a valid page contains no matching records THEN the registration-service SHALL respond `200 OK` with an empty `items` array and the correct `total`.

### REQ-REG-E03 — Get registration

**Endpoint:** `GET /api/v1/registrations/{id}`

**Acceptance criteria:**

1. WHEN `{id}` identifies an existing registration THEN the registration-service SHALL respond `200 OK` with the OpenAPI-compliant `Registration` body.
2. IF `{id}` does not identify an existing registration THEN the registration-service SHALL respond `404 Not Found` with error code `NOT_FOUND`.

### REQ-REG-E04 — Cancel registration

**Endpoint:** `PATCH /api/v1/registrations/{id}`

**Acceptance criteria:**

1. WHEN `{id}` identifies a confirmed registration and the body is exactly `{"status":"cancelled"}` THEN the registration-service SHALL apply REQ-REG-B07 and respond `200 OK` with the updated registration.
2. IF `{id}` does not identify an existing registration THEN the registration-service SHALL respond `404 Not Found` with error code `NOT_FOUND`.
3. IF the body is empty, malformed, contains additional fields, or lacks `status` THEN the registration-service SHALL respond with the platform-standard JSON error and SHALL NOT mutate the registration.

### REQ-REG-E05 — Delete registration

**Endpoint:** `DELETE /api/v1/registrations/{id}`

**Acceptance criteria:**

1. WHEN `{id}` identifies an existing registration THEN the registration-service SHALL remove it and respond `204 No Content` with an empty body.
2. IF `{id}` does not identify an existing registration THEN the registration-service SHALL respond `404 Not Found` with error code `NOT_FOUND`.

### REQ-REG-E06 — Registration statistics

**Endpoint:** `GET /api/v1/registrations/stats?event_id=`

**Acceptance criteria:**

1. WHEN a valid existing event ID is supplied THEN the registration-service SHALL return the statistics defined by REQ-REG-B08 with `200 OK`.
2. IF the event does not exist THEN the registration-service SHALL return `404 NOT_FOUND`.
3. IF the parameter is missing or invalid THEN the registration-service SHALL return `422 VALIDATION_ERROR`.
4. IF event-service is unavailable THEN the registration-service SHALL return `503 DEPENDENCY_UNAVAILABLE`.

### REQ-REG-E07 — PUT is not supported

**Endpoint:** `PUT /api/v1/registrations/{id}`

**Acceptance criteria:**

1. WHEN PUT is requested for any registration ID THEN the registration-service SHALL respond `405 Method Not Allowed` with error code `METHOD_NOT_ALLOWED` using the standard JSON error envelope.
2. WHEN PUT is rejected THEN the registration-service SHALL NOT read or mutate registration state and SHALL NOT call another service.

### REQ-REG-E08 — Health check

**Endpoint:** `GET /health`

**Acceptance criteria:**

1. WHEN `/health` is requested THEN the registration-service SHALL respond `200 OK` with exactly `{"status":"ok","service":"registration-service"}`.
2. WHEN user-service or event-service is unavailable THEN `/health` SHALL continue to report local process health and SHALL NOT call either dependency.

## 5. Error Contract

### REQ-REG-ERR01 — Strict error envelope

1. WHEN the registration-service returns an error THEN it SHALL return JSON shaped as:

```json
{
  "error": {
    "code": "UPPER_SNAKE_CASE",
    "message": "Human-readable explanation",
    "details": {}
  }
}
```

2. WHEN no structured detail is needed THEN `details` SHALL be an empty JSON object.
3. IF an error response contains undeclared outer or inner properties THEN it SHALL be considered contract-incompatible.

| Condition | Status | Code |
|---|---:|---|
| Malformed JSON | 400 | `MALFORMED_JSON` |
| Local registration or stats event not found | 404 | `NOT_FOUND` |
| Duplicate confirmed registration | 409 | `ALREADY_REGISTERED` |
| Event at capacity | 409 | `EVENT_FULL` |
| Invalid input/filter/pagination | 422 | `VALIDATION_ERROR` |
| Missing create reference | 422 | `REFERENCE_NOT_FOUND` |
| Event not published | 422 | `EVENT_NOT_OPEN` |
| Invalid status change | 422 | `INVALID_STATUS_TRANSITION` |
| Unsupported PUT | 405 | `METHOD_NOT_ALLOWED` |
| Dependency failure | 503 | `DEPENDENCY_UNAVAILABLE` |

## 6. Platform, Persistence, and Quality Requirements

### REQ-REG-N01 — Environment-driven runtime

1. WHEN the service starts THEN it SHALL read `PORT` from the environment and default to `5003` only when absent.
2. WHEN user-service is called THEN its base URL SHALL come from `USER_SERVICE_URL`, defaulting to `http://localhost:5001` only when absent.
3. WHEN event-service is called THEN its base URL SHALL come from `EVENT_SERVICE_URL`, defaulting to `http://localhost:5002` only when absent.
4. WHEN the acceptance suite injects alternate ports and URLs THEN the service SHALL use them without source changes.

### REQ-REG-N02 — Pluggable standard-library persistence

1. WHEN `STORAGE_BACKEND` is absent or `memory` THEN registrations SHALL use in-process persistence.
2. WHEN `STORAGE_BACKEND=json` THEN registrations SHALL persist under `DATA_DIR` using standard-library JSON/file APIs.
3. WHEN `STORAGE_BACKEND=sqlite` THEN registrations SHALL persist under `DATA_DIR` using standard-library `sqlite3`.
4. WHEN `DATA_DIR` is absent THEN file-backed storage SHALL default to `./data`.
5. IF the backend changes THEN routes and business logic SHALL require no modification.
6. The service SHALL NOT use an external DBMS, ORM, or non-standard persistence library.

### REQ-REG-N03 — Verification quality

1. WHEN repository tests execute THEN they SHALL verify equivalent behavior for memory, JSON, and SQLite using `tmp_path` for file backends.
2. WHEN HTTP client tests execute THEN user-service and event-service calls SHALL be mocked with `responses`, including 200, 404, 5xx, timeout, and connection failure paths.
3. WHEN endpoint tests execute THEN at least one response for every endpoint SHALL be validated with `contracts/validator.py::assert_matches_contract`.
4. WHEN custom cross-service tests execute THEN real HTTP services SHALL verify a positive registration, missing references returning 422, and unavailable dependencies returning 503.
5. WHEN coverage is measured for the registration-service application package THEN line coverage SHALL be at least 80%.
6. Every test SHALL be traceable to one or more `REQ-REG-*` identifiers through a marker, test name, or docstring.
