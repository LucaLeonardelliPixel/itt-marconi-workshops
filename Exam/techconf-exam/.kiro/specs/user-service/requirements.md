# Requirements Document

**Service:** user-service  
**Base path:** `/api/v1/users`  
**Port:** 5001 (dev) · 15001 (acceptance)  
**Contract:** `contracts/openapi/user-service.yaml`  
**Status:** Mandatory

---

## Introduction

The user-service is the identity registry for the TechConf platform. It stores and manages conference participants across three roles: attendees, speakers, and organizers. All other platform services that need to verify a person's identity or role delegate to this service. It has no upstream HTTP dependencies of its own.

---

## Glossary

| Term | Definition |
|---|---|
| User | A person registered on the TechConf platform, identified by a unique UUID. |
| Attendee | Default role assigned to a newly registered user. |
| Speaker | A user who presents a session at the conference. |
| Organizer | A user with administrative responsibilities for the conference. |
| Email normalisation | The process of converting an email address to all-lowercase before storage and comparison. |
| UserCreate | The request body schema accepted by POST and PUT operations (all required fields present). |
| UserUpdate | The request body schema accepted by PATCH operations (all fields optional, at least one required). |
| User (response) | The full resource representation returned by the service, including server-generated fields. |
| UserPage | The paginated list response wrapping an array of User objects with pagination metadata. |

## Resource Schema

### Fields accepted on creation / full replacement (`UserCreate`)

| Field | Type | Required | Constraints |
|---|---|---|---|
| `first_name` | string | Yes | 1–50 characters |
| `last_name` | string | Yes | 1–50 characters |
| `email` | string | Yes | Valid email format; unique across all users (case-insensitive) |
| `company` | string | No | max 100 characters; nullable |
| `role` | enum | No | `attendee` \| `speaker` \| `organizer`; default `attendee` |

### Fields accepted on partial update (`UserUpdate`)

Same as `UserCreate` but all fields are optional (at least one must be present).

### Read-only fields (server-generated, never accepted from client)

| Field | Type | Notes |
|---|---|---|
| `id` | UUID v4 | Generated by the server at creation |
| `created_at` | ISO 8601 UTC datetime | Set at creation, never changes |
| `updated_at` | ISO 8601 UTC datetime | Updated on every successful modification |

### Full response shape (`User`)

```json
{
  "id": "<uuid>",
  "first_name": "Alice",
  "last_name": "Smith",
  "email": "alice@example.com",
  "company": "Acme",
  "role": "organizer",
  "created_at": "2026-10-01T10:00:00Z",
  "updated_at": "2026-10-01T10:00:00Z"
}
```

`additionalProperties: false` — extra fields in the response body are a contract violation.

## Business Rules

### REQ-USR-B01 — Email Uniqueness

**User story:** As a platform administrator, I want each email address to be registered only once, so that users have a unique, unambiguous identity.

**Acceptance criteria:**

1. WHEN a POST or PUT or PATCH request is received with an `email` value AND a different user with the same email (compared case-insensitively) already exists in the store THEN the user-service SHALL respond `409 Conflict` with error code `EMAIL_ALREADY_EXISTS`.
2. WHEN the email belongs to the same user being updated (PUT/PATCH on `/{id}`) THEN the user-service SHALL treat the email as unchanged and SHALL NOT raise a conflict.
3. IF the comparison is performed case-insensitively (e.g. `Alice@Example.COM` == `alice@example.com`) THEN the user-service SHALL consider those addresses identical for uniqueness purposes.

---

### REQ-USR-B02 — Email Normalisation

**User story:** As a developer integrating with the platform, I want emails stored in a canonical form, so that lookups and comparisons are predictable.

**Acceptance criteria:**

1. WHEN a user is created or updated with an `email` value THEN the user-service SHALL store the email in all-lowercase form.
2. WHEN the stored email is returned in any response THEN the user-service SHALL return the lowercase-normalised value.

---

### REQ-USR-B03 — List Filtering

**User story:** As a service consumer, I want to filter the user list by `role` and/or `email`, so that I can quickly locate specific subsets of users.

**Acceptance criteria:**

1. WHEN `GET /api/v1/users?role=organizer` is requested THEN the user-service SHALL return only users whose `role` equals the supplied value.
2. WHEN `GET /api/v1/users?email=alice@example.com` is requested THEN the user-service SHALL return only users whose stored (lowercase) email equals the supplied value (case-insensitive comparison).
3. WHEN both `role` and `email` query parameters are supplied THEN the user-service SHALL apply both filters (logical AND).
4. IF the `role` query parameter contains a value not in `{attendee, speaker, organizer}` THEN the user-service SHALL respond `422 VALIDATION_ERROR`.

## Endpoint Requirements

### REQ-USR-E01 — Create User `POST /api/v1/users`

**User story:** As a new conference participant, I want to register my profile, so that I can be identified across the platform.

**Acceptance criteria:**

1. WHEN a POST request is received with a valid JSON body containing all required fields THEN the user-service SHALL create a new user, assign a server-generated UUID v4 `id`, set `created_at` and `updated_at` to the current UTC time, default `role` to `attendee` if omitted, and respond `201 Created`.
2. WHEN responding 201 THEN the user-service SHALL include a `Location` header with value `/api/v1/users/{id}`.
3. WHEN responding 201 THEN the response body SHALL conform to the `User` schema.
4. IF the request body is not valid JSON THEN the user-service SHALL respond `400 Bad Request` with error code `MALFORMED_JSON`.
5. IF any required field (`first_name`, `last_name`, `email`) is missing or empty THEN the user-service SHALL respond `422 Unprocessable Entity` with error code `VALIDATION_ERROR`.
6. IF any field violates its length or format constraint (see schema table) THEN the user-service SHALL respond `422 Unprocessable Entity` with error code `VALIDATION_ERROR`.
7. IF the email is already taken (see REQ-USR-B01) THEN the user-service SHALL respond `409 Conflict` with error code `EMAIL_ALREADY_EXISTS`.
8. IF the request body contains fields not defined in `UserCreate` (e.g. `id`, `created_at`) THEN the user-service SHALL respond `422 VALIDATION_ERROR` (contract: `additionalProperties: false`).

---

### REQ-USR-E02 — List Users `GET /api/v1/users`

**User story:** As an event organizer, I want to browse all registered users with optional filters and paging, so that I can manage conference attendees.

**Acceptance criteria:**

1. WHEN a GET request is received THEN the user-service SHALL return `200 OK` with a paginated response.
2. WHEN no pagination parameters are supplied THEN the user-service SHALL default to `page=1` and `page_size=20`.
3. WHEN `page_size` exceeds 100 THEN the user-service SHALL respond `422 VALIDATION_ERROR`.
4. WHEN `page` is less than 1 or `page_size` is less than 1 THEN the user-service SHALL respond `422 VALIDATION_ERROR`.
5. WHEN filters are applied (REQ-USR-B03) THEN `total` SHALL reflect the count of matching users, not all users.
6. The response body SHALL conform to the `UserPage` schema: `{"items": [...], "page": <int>, "page_size": <int>, "total": <int>}`.

---

### REQ-USR-E03 — Get User by ID `GET /api/v1/users/{id}`

**User story:** As a downstream service (event-service, registration-service), I want to fetch a user by their UUID, so that I can validate their existence and role.

**Acceptance criteria:**

1. WHEN a GET request is received with a valid UUID `id` that exists in the store THEN the user-service SHALL respond `200 OK` with the `User` object.
2. IF the `id` does not match any stored user THEN the user-service SHALL respond `404 Not Found` with error code `NOT_FOUND`.

---

### REQ-USR-E04 — Replace User `PUT /api/v1/users/{id}`

**User story:** As a user, I want to fully replace my profile data, so that I can update all my details at once.

**Acceptance criteria:**

1. WHEN a PUT request is received with a valid `id` and a complete `UserCreate` body THEN the user-service SHALL replace all mutable fields, update `updated_at` to the current UTC time, and respond `200 OK` with the updated `User`.
2. IF the `id` does not match any stored user THEN the user-service SHALL respond `404 Not Found` with error code `NOT_FOUND`.
3. IF the body is missing required fields or violates constraints THEN the user-service SHALL respond `422 VALIDATION_ERROR`.
4. IF the new email is already taken by a different user (REQ-USR-B01) THEN the user-service SHALL respond `409 EMAIL_ALREADY_EXISTS`.
5. `id`, `created_at` SHALL remain unchanged; only `updated_at` changes.

---

### REQ-USR-E05 — Partial Update User `PATCH /api/v1/users/{id}`

**User story:** As a user, I want to update individual fields of my profile without resending all fields, so that partial edits are convenient.

**Acceptance criteria:**

1. WHEN a PATCH request is received with a valid `id` and a partial `UserUpdate` body THEN the user-service SHALL update only the supplied fields, update `updated_at` to the current UTC time, and respond `200 OK` with the updated `User`.
2. IF the `id` does not match any stored user THEN the user-service SHALL respond `404 Not Found` with error code `NOT_FOUND`.
3. IF any supplied field violates its constraint THEN the user-service SHALL respond `422 VALIDATION_ERROR`.
4. IF the new email is already taken by a different user (REQ-USR-B01) THEN the user-service SHALL respond `409 EMAIL_ALREADY_EXISTS`.
5. Fields not present in the PATCH body SHALL retain their current values.
6. `id` and `created_at` SHALL never be modified via PATCH.

---

### REQ-USR-E06 — Delete User `DELETE /api/v1/users/{id}`

**User story:** As a platform administrator, I want to remove a user account, so that stale records can be cleaned up.

**Acceptance criteria:**

1. WHEN a DELETE request is received with a valid `id` that exists in the store THEN the user-service SHALL remove the user and respond `204 No Content` with an empty body.
2. IF the `id` does not match any stored user THEN the user-service SHALL respond `404 Not Found` with error code `NOT_FOUND`.

---

### REQ-USR-E07 — Health Check `GET /health`

**Acceptance criteria:**

1. WHEN a GET request is received at `/health` THEN the user-service SHALL respond `200 OK` with body `{"status": "ok", "service": "user-service"}`.
2. The health endpoint SHALL respond even if the storage backend is empty.

## Error Response Envelope

All error responses (4xx) SHALL use this exact JSON shape (`additionalProperties: false` on both outer and inner objects):

```json
{
  "error": {
    "code": "UPPER_SNAKE_CASE",
    "message": "Human-readable description",
    "details": {}
  }
}
```

| Situation | Status | `code` |
|---|---|---|
| Malformed / non-JSON body | 400 | `MALFORMED_JSON` |
| Missing or invalid field | 422 | `VALIDATION_ERROR` |
| Duplicate email | 409 | `EMAIL_ALREADY_EXISTS` |
| Resource not found | 404 | `NOT_FOUND` |

---

## Pagination Contract

All list responses SHALL include:

```json
{
  "items": [ /* User objects */ ],
  "page": 1,
  "page_size": 20,
  "total": 57
}
```

- `total` is the count of all users matching the active filters.
- `items` contains at most `page_size` users for the requested `page`.
- `additionalProperties: false` applies to the `UserPage` object.
